# Incidents

`docs/runbook.md` §7.3에 따라 사고 발생 시 본 디렉토리에 5W1H 요약을 남긴다. 미래의 본인 또는 후임 운영자가 같은 사고를 반복하지 않도록 흔적을 남기는 게 목적.

## 파일명 규약

```
YYYY-MM-DD-짧은요약.md
```

- 날짜는 사고 **발생일** 기준 (검출일이 아니라).
- 짧은요약은 한국어 1~3 단어, 공백 대신 `-`. 예: `2026-05-15-signup-500.md`, `2026-06-02-supabase-key-rotation.md`.
- 같은 날 두 건 발생하면 뒤에 `-1`, `-2`.

## 작성 시점

- 사고 1차 조치(`docs/runbook.md` §7.2 표 참조)가 끝난 직후 5분 내로 초안.
- 영향 범위가 1주 이상이거나 외부 보고가 필요한 사고면 GitHub Issue도 함께 생성하고 본 파일에서 링크.
- 단순 알림성(예: 일시적 5xx 1건)은 본 파일 없이 주간 점검 메모로 충분.

## 5W1H 템플릿

새 사고 파일을 만들 때 아래 템플릿을 복사해서 채운다.

```markdown
# YYYY-MM-DD 짧은요약

- **Severity**: SEV1 (서비스 중단) | SEV2 (일부 기능 손상) | SEV3 (관측 이상, 사용자 영향 미미)
- **Detected**: YYYY-MM-DD HH:MM KST — 검출 경로 (Vercel 로그 / 사용자 제보 / 정기 점검 등)
- **Resolved**: YYYY-MM-DD HH:MM KST 또는 "ongoing"

## What
무엇이 일어났는가. 한 문장.

## When
- 발생 시각 (추정 가능 시):
- 검출 시각:
- 종료 시각:

## Where
영향 범위 — 어떤 라우트·기능·사용자 그룹.

## Who
- 영향 받은 사용자 수 (추정):
- 대응자:

## Why (Root Cause)
재발 방지에 필요한 만큼만. 추측이면 "추정" 표시.

## How (대응)
- 1차 조치:
- 영구 조치:
- 후속 PR/이슈 링크:

## Lessons
- 무엇을 다르게 할 것인가 (체크리스트, 모니터링 추가, 런북 보강 등).
```

## 보관 원칙

- 본 디렉토리는 git 추적 대상. PII나 시크릿 원문은 절대 포함하지 않는다(키 ID, 마지막 4자리, 해시 정도까지).
- 파일은 삭제하지 않는다. 잘못 작성됐으면 후속 commit으로 정정 표기 (`> 정정: ...`).
